# NAT лаборатория (Н8)

Два истински браузъра зад симулирани NAT-ове, на един Linux компютър, без облак. Всеки сценарий
трябва да даде очаквания резултат: връзка и съобщение в двете посоки, или правилната диагноза на
двата екрана.

```
sudo -E node scripts/natlab/run.mjs                      # всички сценарии
sudo -E node scripts/natlab/run.mjs --only udp-blocked   # един
sudo -E node scripts/natlab/run.mjs --browser-b firefox  # Chromium ↔ Firefox (FIREFOX_PATH=…)
```

Трябват Linux, root (network namespaces), `iproute2` и `iptables`. В GitHub върви всеки понеделник
и при промяна в `src/p2p/` (`.github/workflows/natlab.yml`, Chromium ↔ Chromium и Chromium ↔ Firefox).
Резултатът е в `natlab-report.json` и в обобщението на workflow-а.

## Как е построена

```
 hA (10.0.1.2 / 2001:db8:a::2)                 hB (10.0.2.2 / 2001:db8:b::2)
    │                                              │
 rA  NAT  203.0.113.10                         rB  NAT  203.0.113.20
    └──────── wan мост 203.0.113.0/24, 2001:db8:ffff::/64 ────────┘
                              │
                 STUN 203.0.113.1 / [2001:db8:ffff::1]:3478
```

- Всяко поле е отделен network namespace. Адресите са от документационните диапазони и не излизат в интернет.
- **STUN** е `scripts/natlab/stun.mjs`: само Binding, около 150 реда, без зависимости.
- **Приложението** е билд с `VITE_STUN_URLS` (лабораторният STUN вместо Google) и `VITE_NATLAB=1`
  (дава на теста декодера на собствения QR). В изданията и двете липсват.
- **Хората** са `scripts/natlab/agent.mjs`: браузър в своя namespace, който минава през същите
  екрани като човек: профил, покана, отговор, 12 думи, съобщение.

## NAT типове

| Тип | Как | Какво значи |
|---|---|---|
| cone (пълен) | `MASQUERADE` навън + `DNAT` на нов входящ UDP към единственото устройство | Портът не зависи от адресата (EIM), а входящото не се филтрира (EIF). Като домашен рутер с устройството в DMZ или UPnP. |
| symmetric | `MASQUERADE --random-fully` | Нов случаен порт за всеки адресат. Като много мобилни оператори (CGNAT) и корпоративни мрежи. |

Само `MASQUERADE` не е cone в Linux: първите проверки на другия идват, преди нещо да е излязло,
conntrack ги записва, и този запис взима точно порта, който изходящото съпоставяне иска. Linux
избира друг порт и всяка следваща проверка подновява сблъсъка. Затова cone тук е пълен cone.

## Сценарии

| Сценарий | Очаквано | Диагноза (A / B) |
|---|---|---|
| cone ↔ cone | връзка | |
| cone ↔ cone със загуби | връзка | 2% загуба; +60±20 ms, където има `netem` |
| cone ↔ symmetric | връзка | пълният cone приема новия порт на другия (peer-reflexive) |
| symmetric ↔ symmetric | няма връзка | „И двете устройства са зад NAT…“ / същото |
| IPv6 ↔ IPv6 | връзка | без NAT, маршрутизиран |
| само IPv6 ↔ само IPv4 | няма връзка | „Едното устройство е само с IPv6…“ / същото |
| блокиран UDP | няма връзка | „Твоята мрежа не пропуска UDP…“ / „Мрежата на другия човек не пропуска UDP…“ |

Диагнозата е `diagnoseFailure()` в `src/p2p/network.ts`. Тя сравнява кандидатите на двете страни
(своите и тези от поканата или отговора). Преди тази функция екранът казваше само „Мрежата може да блокира директната връзка“.

## Когато нещо липсва

- **Без `tc netem`** (някои контейнери): загубите се правят с `iptables -m statistic`, а закъснение няма.
- **Без IPv6 в ядрото**: двата IPv6 сценария се пропускат с бележка, останалите вървят без IPv6.
- **Заседнал опит** (нито връзка, нито съобщение и на двата екрана): повтаря се веднъж, както в
  другите e2e тестове. Грешен резултат не се повтаря.
